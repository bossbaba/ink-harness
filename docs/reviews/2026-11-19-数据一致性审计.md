# 2026-11-19 数据一致性审计

审计对象：`src/`（Vue 3 前端）、`src-tauri/src/`（Rust + SQLite 后端）。

审计方式：三路并行只读扫描 + 关键结论逐条回读源码复核，最后用 `cargo test` / `vue-tsc` / `npm run build` 验证改动。

问题编号：`D-xx`（Data consistency）。状态：`已修复` = 本次落地并验证；`部分修复` = 主路径修好、边角留待后续；`待办` = 已定位未动，附建议。

## 一、总体结论

数据库层本身不脏：外键约束、级联删除矩阵、事务边界、字数聚合口径基本一致，`PRAGMA foreign_keys` 已开，删除章节会级联清掉场景、版本与伏笔引用。

真正的风险在**"同一份数据被多处缓存副本重复提交"**：

1. 正文与章节元数据都是**整篇/整对象覆盖**，DB 侧没有版本校验 —— 写作台自动保存、审稿回写、工作流审批、版本恢复、大纲编辑之间互相覆盖，最后写者赢。
2. 页面被 keep-alive 缓存，**跨页写入没有统一的失效通知** —— 大纲改了章节、工作流写了正文，另一个页面仍拿着旧副本。
3. 围绕正文的**派生数据**（RAG 索引、章节字数、发布预览、摘要）没有跟随失效。

本次已把第 2 类的主链路补齐、第 1 类加上乐观锁、第 3 类按危害排序处理。

## 三、落地要点

**乐观锁协议**：整篇/整对象写入都带「我读到的版本」，后端比对不一致就返回 `conflict`，前端不重试、不覆盖。

正文与元数据用了两个不同的版本标记，原因是它们的写入频率与语义不同：

- **正文**用新增的 `chapter.content_revision`（整数，正文每存一次 +1）。不直接用 `updated_at`，是因为改标题/摘要/状态也会刷新时间戳——那会把写作台手里的正文基准顶掉，导致「改个标题就保存冲突」。
- **章节元数据**用 `chapter.updated_at`。正文保存也会推进它，所以元数据冲突其实覆盖了「正文刚被写、状态已从待写变写作中」的情况。
  `updated_at` 的时间精度只有毫秒，因此写入时做了**严格递增**处理（同一毫秒内第二次写会进位 +1ms），否则连点保存时基准不变，乐观锁会静默失效。
- **摘要**单独走 `update_chapter_summary`，只改 summary 且不动时间戳：摘要由 AI 频繁自动更新，不能把 `title/act/status` 一起写回，也不该让 RAG 索引被判过期。

冲突后前端会暂停该章的自动保存（`halted`），把当前文字写入本地备份并提示重新载入；重新载入或恢复版本会解除暂停。

**缓存页刷新约定**：写操作只对「当前页」负责；跨页一致性统一交给 `onReactivated`（`utils/lifecycle.ts`）。新增页面时若读取的是别的页面可写的数据，必须补 `onReactivated`。

**派生数据失效**：正文变化后 RAG 视为 stale，检索阶段直接返回空结果 + `stale` 标记，避免 AI 拿着旧正文继续写；重建是显式动作，不在保存路径里隐式触发。
