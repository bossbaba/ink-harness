## 一、总体结论

整改后的工程骨架仍然合理：命令层不依赖 Tauri 之外的前端概念、service 层无 `tauri::` / `AppHandle`、组件无运行时直连 service/IPC、composables/views 无直连 `@/api/tauri`；路由作用域规范（实体 ID 在 path、query 只做定位），`routeCacheKey` 与两处局部错误边界的 `resetKey` 口径一致；`meta_revision` 从建表、v9 迁移、模型到事务内乐观锁形成闭环；规范守卫与行数红线实测通过。

架构层面的偏差集中在四类：**审批令牌机制的作用被高估**（签发命令本身就是 IPC）、**归属校验下沉不彻底且覆盖不齐**、**基础设施与 service 依赖反转**、**两份文件贴线零余量**。这些不是新引入的功能缺陷，而是上一轮整改在「放哪一层 / 边界算不算数」上的遗留问题。

按影响排序：**AR-01 > AR-02 / AR-03 / AR-04 > AR-05 > 其余**。

## 三、合规结论

1. **分层与依赖**：新增 `services/approval.rs`、`commands/ownership.rs` 的模块注册完整（`commands/mod.rs:15`、`services/mod.rs:4`、`lib.rs`）；service 层未出现 Tauri IPC 类型；endpoint 校验集中在 `services/provider_kind.rs`，脱敏集中在 `services/guardrails.rs`，除 AR-04 外无新的重复实现。
2. **路由与页面**：全局页无前缀、作品内统一 `/projects/:projectId/*`，实体 ID 在 path；query 只用于过滤/定位，无「一个意图两个页面」。`routeCacheKey(path, reloadKey)` 忽略 query，与 `App.vue` 的 `reset-key="route.path"`、`ProjectPublishView` 的 `tab`、`ProjectReviewView` 的 `createdAt + layer` 口径一致。
3. **契约闭环**：前后端 `projectId` / `approvalToken` 参数签名一致；`metaRevision` 从 DB 列 → v9 迁移 → `Chapter` 模型 → TS 类型 → 事务内条件更新形成闭环，正文保存不推进该字段。仅 AR-03 的 outline 命令未透传作用域。
4. **规范与注释**：新增/改动代码的公共函数与复杂分支普遍有中文「为什么」注释；未发现机翻腔或大段注释掉的死代码，失效注释仅 AR-07 一处；UI 普遍使用 naive-ui、语义色变量与 `@container`，违反项仅 AR-08 的两个原生按钮。
5. **行数**：无文件超过 500 行；逼近红线的还有 `services/rag.rs 425`、`services/outline.rs 407`、`db/schema.rs 400`、`services/rag/tests_bounds.rs 497`（未改动），新增逻辑前应先拆。

## 五、整改建议顺序

1. **先定调审批令牌**（AR-01）：明确它是「防误调用」还是「安全边界」；若是后者，重新设计签发路径，不要只把命令暴露给前端。
2. **收敛归属校验**（AR-02 / AR-03）：下沉到 service，补齐 outline 命令的 `project_id`，恢复错误信息语义。
3. **修依赖方向**（AR-04）：向量表名枚举下沉，清理逻辑单一真源。
4. **补红线余量与守卫**（AR-05 / AR-06）：拆 `useWritingDesk`，守卫覆盖 `@tauri-apps/*`。
5. **文档与 UI 一致性**（AR-07 / AR-08）：修正注释、统一按钮、给双端脱敏加一致性测试。
