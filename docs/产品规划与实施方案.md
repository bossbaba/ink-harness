# INK-HARNESS 产品规划与实施方案

> AI 辅助写作桌面软件：辅助作者完成一部作品从构思、创作、编辑到出版发布的全流程。
> 版本：v1.0 ｜ 日期：2026-11-17

---

## 1. 项目概述

### 1.1 产品定位

一个**本地优先的 AI 写作工作室**（桌面软件）。作者主导、Agent 辅助，覆盖 `构思 → 大纲 → 设定 → 初稿 → 编辑审稿 → 排版出版 → 发布运营` 的完整链路。

核心理念不是"一键生成一本书"，而是**人在环路（human-in-the-loop）**：每个阶段由 AI 产出候选，作者审阅、修改、确认后再进入下一阶段。所有上下文沉淀到统一的"作品记忆库（Story Bible）"，以保证长篇作品的一致性。

### 1.2 前置假设

- "作品"以**长篇小说 / 非虚构长文**为主，架构上可扩展到剧本。
- 软件形态为**桌面应用**，数据留在用户机器，接本地模型时可完全离线工作。
- AI 后端**模型无关**：既可接入本地大模型，也可接入三方大模型，业务代码与具体模型解耦。

### 1.3 三项核心约束

1. **不使用 React 作为前端框架** —— 采用 Vue 3。
2. **模型来源双轨** —— 本地大模型 + 三方大模型统一抽象，按任务路由、可隐私分级。
3. **桌面软件** —— 本地优先、离线可用、零服务器成本（除非用户主动使用三方 API）。

## 2. 需求规划

### 2.1 功能模块（按写作生命周期）

| 阶段 | 模块                              | 核心能力                                                                                                            |
| ---- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 立项 | **构思向导**                      | 访谈式提问（题材/主题/核心冲突/目标读者/风格）→ 生成书名候选、一句话梗概、简介、读者画像                            |
| 设计 | **世界观与设定库（Story Bible）** | 人物档案（含人物弧光）、地点、组织、时间线、术语表、伏笔；关系图；一致性冲突提醒                                    |
| 设计 | **大纲与结构**                    | 三幕/起承转合、章节表、场景卡（POV/时间/地点/摘要）、拖拽排序、伏笔的"铺设→回收"追踪                                |
| 创作 | **写作台**                        | 富文本编辑、专注模式、AI 续写/改写/扩写/缩写/润色/对话生成、风格锁定（学习已写章节的 voice）、字数与进度统计        |
| 创作 | **AI Copilot**                    | 右侧对话面板，可 `@引用` 设定/章节；流式输出；建议以卡片呈现，可"插入/替换/忽略"                                    |
| 打磨 | **编辑与审稿**                    | 结构/一致性/语言三层审稿报告、逻辑漏洞与人物动机检查、Diff 逐条接受/拒绝、批注                                      |
| 发布 | **出版中心**                      | 排版模板（网络连载/电子书/纸质稿）、EPUB/PDF/DOCX 导出、封面需求简报、简介/标签/书名/投稿信生成、平台发布清单与日历 |
| 支撑 | **模型管理**                      | Provider 配置、本地模型检测/下载、测试连接、能力标签、任务路由、密钥管理、用量与成本看板                            |
| 支撑 | **知识库 / RAG**                  | 导入参考资料（文档/网页）向量化，写作时检索引用                                                                     |

### 2.2 非功能需求

- **长文一致性**：全书设定、人名、时间线、风格统一（靠 Story Bible + 摘要压缩 + 检索注入上下文解决）。
- **流式体验**：AI 输出逐字到达，可随时中断。
- **可回溯**：草稿版本快照，AI 每次生成的输入/输出可审计。
- **成本可控**：token 统计与预算上限，支持便宜模型做 routine 任务。
- **隐私分级**：作品可标记"仅本地处理"，强制只走本地模型，三方通道不可见。
- **离线可用**：接本地模型时断网可正常工作。

## 3. 技术架构

### 3.1 桌面技术栈

| 层           | 选型                                                                                                                                       | 理由                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| 桌面壳       | **Tauri 2**（首选）/ Electron（备选）                                                                                                      | 体积小（~10MB vs ~150MB）、内存低、原生窗口；Rust 后端适合进程管理与文件读写；不引入 React                        |
| 前端框架     | **Vue 3.5 + Vite 7 + TypeScript 5**                                                                                                        | 组合式 API 适合复杂交互状态，用户已熟悉 Vue 生态                                                                  |
| 状态/路由    | **Pinia + Vue Router 4**                                                                                                                   | Vue 官方方案，类型友好                                                                                            |
| 代码检查     | **Biome 2.6**（`biome check` 统一 lint+format，已移除 ESLint）                                                                            | 单工具链、快；`*.vue` 关闭 `noUnusedImports`/`noUnusedVariables`（Biome 看不到 `<template>` 用法会误报），`*.ts` 全量检查 |
| 样式预编译   | **Sass 1.108**（模块化分层：`_tokens` / `_mixins` / `_base` / `_bridge`，`@use` 组织）                                                     | 用户指定 Sass；纸墨主题令牌集中管理                                                                               |
| UI 框架      | **C 混合方案**：Naive UI 2.45（DataTable/Tree/Modal/Select 等功能重组件）+ MacVue `@macvue/core` 0.1（按钮/开关/毛玻璃等 AppKit 原生控件） | 无成熟 Vue macOS 组件库；混合方案兼顾功能完整度与原生观感。MacVue 0.1 的 token 未稳定，桥接层集中覆盖，升级成本低 |
| 主题桥接     | Sass `_bridge.scss` 覆盖 `--macvue-*` + `src/theme/naive.ts` 的 `GlobalThemeOverrides`                                                     | 两套库的观感统一到纸墨色板                                                                                        |
| 富文本编辑器 | **TipTap 2**（`@tiptap/vue-3`，ProseMirror 内核）                                                                                          | 长文写作最佳底座，支持自定义节点与 AI 内联工具条                                                                  |
| 本地存储     | **SQLite**（`@tauri-apps/plugin-sql`，sqlx）                                                                                               | 桌面标配，单文件、免运维、可备份；Tauri 无 Node 运行时，不用 better-sqlite3                                       |
| 向量检索     | **方案 B 双连接**：Rust `infrastructure/db.rs` 开两个 rusqlite 连接（biz 业务 / vec 向量）+ `sqlite-vec 0.1.9`（见 3.1.1 / 3.6.1）        | 嵌入式，替代服务端 pgvector；不让前端绕过分层直连 DB                                                             |
| 本地模型     | **Ollama**（检测或捆绑为 sidecar）/ llama.cpp 内嵌                                                                                         | 见 3.3                                                                                                            |
| 模型代理     | **Tauri 命令层代理三方 API**（Rust `reqwest`）                                                                                             | 密钥存系统钥匙串，前端不接触                                                                                      |
| 文件导出     | 前端生成或 Tauri 命令                                                                                                                      | EPUB/DOCX/PDF 均在端侧完成，无需服务器                                                                            |
| 自动更新     | Tauri updater                                                                                                                              | 桌面标配                                                                                                          |

> 备选：若希望纯 Node 技术栈、完全不接触 Rust，可换 Electron；但体积与资源占用明显上升。

#### 3.1.1 数据持久化决策（2026-11-17）

- **存储位置**：Tauri `app_data_dir()` 下的单文件 `ink-harness.db`（本机实测：`~/Library/Application Support/com.inkharness.app/ink-harness.db`）。单文件便于备份/迁移/展示路径；业务表与向量表共用此文件。
- **双连接落地**：均在 Rust `infrastructure/db.rs` 用 `rusqlite` 打开（`biz` / `vec`），`sqlite-vec` 经 `sqlite3_auto_extension` 进程级注册一次（Once），WAL + `busy_timeout(2s)`。不让前端直连 DB，以保持 `commands → services` 分层不被绕过。

#### 3.2.1 代码分层（2026-11-17 架构重构）

核心原则：**单向依赖，上层依赖下层，下层绝不反向引用**。

**后端（Rust）严格四层：**
```
src-tauri/src/
├── main.rs / lib.rs        仅装配注册
├── models/                 数据契约（serde structs），被所有层引用
│   ├── chat.rs（ChatMessage/ChatParams/ChatChunk）
│   └── provider.rs（ProviderConfig/OllamaStatus）
├── infrastructure/         外部设施，无业务逻辑
│   ├── keychain.rs（系统钥匙串封装）
│   ├── llm_http.rs（reqwest client 构造 + Ollama 常量）
│   └── db.rs（P2 数据库）
├── services/               领域逻辑，不依赖 Tauri，可纯 Rust 单测
│   ├── gateway.rs（provider 解析 / 隐私分级 / SSE 流式代理 / SseParser）
│   └── ollama.rs（服务检测）
└── commands/               Tauri 命令层，薄适配：入参校验 + 调 service
    ├── model.rs / ollama.rs / keychain.rs
```
依赖方向：`commands → services → infrastructure → models`。
流式输出经**回调解耦**：`services::gateway::stream_chat(&state, &params, |chunk| ...)` 接收 `FnMut(ChatChunk)`，commands 层把回调接到 `Channel`；service 不认识 Tauri。SSE 解析抽成纯 `SseParser`，5 个单测覆盖增量分片/[DONE]/角色块等。

**前端分层：**
```
src/
├── app/           main.ts / App.vue / router —— 应用装配
├── api/           tauri.ts —— 仅 IPC 封装（基础设施）
├── services/      modelRouter.ts —— 领域服务（依赖 api）
├── stores/        Pinia 全局状态
├── types/         model.ts + index.ts（按域拆分，统一从 @/types 导入）
├── components/    通用 UI 组件（不含业务）
├── views/         页面：组装 services + components
├── styles/        设计系统（tokens/mixins/base/theme/bridge）
└── theme/         第三方库主题配置
```
依赖方向：`views → services → api → IPC`；`views → components → styles`。跨层导入统一用 `@/` 别名，避免相对路径脆弱。

### 3.3 本地 + 三方模型接入

| 场景                                                        | 实现方式                                                                      | 说明                             |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------- |
| 本地模型（起步）                                            | 检测系统是否已安装 Ollama（`GET localhost:11434/api/tags`），未安装则引导安装 | 零捆绑体积，用户自管模型         |
| 本地模型（进阶）                                            | 把 Ollama/llama.cpp 作为 Tauri sidecar 随应用打包                             | 开箱即用，但安装包增大，后续迭代 |
| 三方 OpenAI 兼容类（DeepSeek/通义/豆包/智谱/Moonshot/Groq） | Tauri 命令层用 `reqwest` 代理请求，密钥从系统钥匙串读取                       | 前端只发模型 ID 与内容           |
| 非兼容三方（Claude / Gemini）                               | Tauri 侧做协议转换，或引入轻量 Rust LLM 客户端库                              | 统一成内部消息格式               |
| 隐私分级                                                    | `ModelRouter` 强制"仅本地"任务只走 Ollama，三方通道不接收数据                 | 端侧执行，比服务端更可信         |

#### 3.3.1 请求链路与流式方案（2026-11-17 决策）

- **请求链路：全走 Rust 代理**。所有 LLM 请求经 `invoke → Rust reqwest → 目标模型`。理由：本地 Ollama 的 CORS 由 `OLLAMA_ORIGINS` 控制，Tauri origin（`tauri://localhost`）默认不在允许列表，前端直连需用户手动配置；且密钥必须留在系统钥匙串、隐私分级须端侧强制。混合/全前端方案均否决。
- **流式通道：Tauri `Channel<ChatChunk>`**。每次 invoke 独立 channel，Rust 逐块 `send()`，`Drop` 时自动清理；不用全局 emit/listen（易泄漏、多请求冲突）。
- **实现位置**：`src-tauri/src/model_gateway.rs`（Provider 管理、Ollama 检测、钥匙串、`chat_completions` 流式命令、隐私拦截）。前端封装在 `src/api/tauri.ts` 与 `src/api/modelRouter.ts`。
- **已知限制**：Tauri 前端 `Channel` 无公开 `close()`，因此**中途取消**尚未实现；当前 Channel 在 Rust 命令返回/出错时自动清理。后续用取消令牌（cancel token）补上。

#### 3.3.2 模型管理（2026-11-17）

- **配置持久化**：Provider 存 `provider_config` 表，`models_json` 保存已启用模型及其上下文窗口；首次启动种入 `ollama-local`，用户删除后不会自动复活。
- **密钥策略**：数据库只存 `api_key_ref`，密钥明文经 `keychain_set` 写入系统钥匙串；新建 Provider 时先落库拿到 id，再按 `provider:<id>` 写入，保证引用键稳定。
- **连接探测**：`probe_provider` 依次尝试 `{base}/models`、`{base}/v1/models`、`{base}/api/tags`，兼容 OpenAI `data[].id` 与 Ollama `models[].name`；保存前可用临时密钥测试，不落库。
- **地址归一化**：本地 Provider 填 `http://localhost:11434` 时保存自动补 `/v1`；云端地址不擅自补路径。
- **与路由的关系**：`ModelRouter` 由「Provider + 已启用模型」派生 `ModelInfo`（provider/source/上下文窗口），再按任务与策略选模型；模型标识统一为 `providerId:modelId`，网关直接读 SQLite 配置（原 `GatewayState` 内存实现移除）。

### 3.5 任务级路由

每个已接入模型登记能力标签，写作台的每个 AI 动作按标签选模型：

| AI 任务               | 路由偏好                 | 说明                     |
| --------------------- | ------------------------ | ------------------------ |
| 构思头脑风暴          | 快/便宜，可本地          | 多轮试错，成本敏感       |
| 长篇续写              | 大上下文窗口             | 需装入前文章节摘要与设定 |
| 编辑润色              | 强指令遵循               | 可用强模型，低频调用     |
| 全书一致性审稿        | 最强推理 / 大上下文      | 一次性高价值任务         |
| 章节摘要 / RAG 向量化 | 便宜模型或本地 embedding | 高频批量                 |

路由策略可切换：**质量优先 / 成本优先 / 隐私优先（仅本地）**，并配置主备模型做故障转移。

### 3.6 数据层

- PostgreSQL + Redis + Celery → **SQLite + 前端任务队列 + Tauri 异步命令**。
- 草稿版本、AI 调用记录、设定、向量索引全存本地 SQLite 文件，用户可自行备份/迁移。
- 长任务（全书一致性扫描、排版导出）用 Web Worker 或 Tauri 后台命令，不阻塞 UI。

#### 3.6.1 向量检索方案（2026-11-17 决策：方案 B 双连接）

**背景**：`tauri-plugin-sql`（前端业务 CRUD）底层是 sqlx，**不暴露 `load_extension`**，无法直接加载 sqlite-vec。经四方案论证（JS 暴力 / 双连接 / 全自研 / LanceDB），选定**方案 B：双连接**。

**实现要点**：

- 业务侧：`@tauri-apps/plugin-sql`（sqlx 连接池）负责项目/章节/设定等 CRUD。
- 向量侧：Rust 侧另开 `rusqlite` 连接，用 `sqlite-vec` **静态编译**（`sqlite3_auto_extension` 进程级注册），管理 `vec0` 虚拟表与 KNN 查询。
- 两侧共享同一个 `libsqlite3-sys 0.30.1`（经 Cargo.lock 确认），因此 auto_extension 注册的 vec 函数对业务连接同样可见。
- 同一数据库文件开启 `journal_mode=WAL` + `busy_timeout(2s)`，支持双连接并发读写。

**版本约束**：`sqlite-vec = "0.1.9"`（稳定版，C 源码自包含）。**禁用 `0.1.10-alpha.*`** —— 该版本 `sqlite-vec.c` 引用了未随包发布的 `sqlite-vec-diskann.c`，会导致 C 编译失败。

**可行性验证**：`src-tauri/tests/vec_spike.rs`（vec0 建表/KNN/业务表共存）与 `dual_connection_spike.rs`（WAL 交替读写、busy_timeout 持锁等待）共 5 个单测全部通过，作为回归测试保留。

**降级路径**：若跨平台打包阶段出现 sqlite-vec 的编译障碍，回退方案 A（embedding 以 BLOB 存 SQLite + JS 端余弦相似度），数据模型不变，仅替换检索实现。

#### 3.6.2 设定库数据模型（2026-11-17）

- 条目类型：`character / place / org / event / term`，统一存 `story_element`，扩展字段放 `detail_json`（`aliases`、`timeStart/timeEnd`、`notes`、`relations`）。关系是有向的 `{targetId, type, label}`，创建/更新时校验目标必须属于同一作品。
- 一致性检查在 Rust service 层完成：规范化名称（去空白 + 小写）检测重名/术语重复；`timeStart/timeEnd` 提取年份做区间重叠与倒置检查；同时报告失效关联。时间解析支持 `2024-03`、`公元前221年`、`19世纪` 等常见写法。
- 双连接均开启 `pragma foreign_keys=ON`，删除作品会级联清理章节、设定、草稿等子记录（有回归测试）。
- 页面边界遵循「功能页面唯一性」：菜单「设定库」进入 `/bible`，跨作品只读汇总；工作台作品卡片进入 `/projects/:projectId/bible`（父路由 `/projects/:projectId` 下的二级路由），仅管理当前作品并支持 CRUD。后者不得出现作品切换器，旧的 `/bible?project=xxx` 会重定向到作品页。作品页三栏布局：左侧筛选列表、中间详情编辑、右侧 SVG 关系图与一致性报告。

#### 3.6.3 大纲数据模型与上下文组装（2026-11-17）

- **数据模型**：`chapter` 增加 `act`（1/2/3）表示三幕，`sort_order` 只在同一幕内递增；`scene` 挂在章节下，携带 `pov / location / time_mark / summary`；`foreshadow` 记录 `setup_chapter_id → payoff_chapter_id` 与状态机 `planned / setup / paid-off`。老库通过 `ensure_column` 做列迁移，`create table if not exists` 不会补列。
- **拖拽语义**：前端只上报「拖到哪」，由 Rust 事务内整组重排：`move_chapter(project_id, chapter_id, target_act, target_index)` 重新编号三幕；`move_scene(scene_id, target_chapter_id, target_index)` 同时重排源章节与目标章节。删除章节时先把伏笔的章节引用置空，再级联删除场景。
- **上下文组装**：`build_project_context(project_id)` 产出一份 Markdown 纯文本（作品信息 → 设定库按类型 → 三幕大纲与场景 → 伏笔铺设/回收），在作品大纲页可预览与复制。该函数是 P4 写作台/Copilot 的唯一上下文入口，避免各页面各拼一份。
- **页面边界**：大纲看板是作品内页面 `/projects/:projectId/outline`，路由名 `project-outline`，不提供全局汇总页；作品卡片提供「进入大纲」直达入口，侧栏二级导航按当前路由显示「作品 · 大纲 / 作品 · 设定库」。

#### 3.6.4 写作台数据模型与自动保存（2026-11-17）

- **正文存储**：`chapter.content` 存 TipTap 文档 JSON 字符串，`chapter.word_count` 存非空白字符数；章节列表查询只 select 字数不读正文，避免一次拉回几十份全文。字数口径统一在前端 `countCharacters`（去空白按字符计数），后端只持久化，不再自行推算。
- **自动保存**：编辑器输入后 1.2s 防抖落库；切章、隐藏窗口、页面卸载时立即 flush。保存目标固定为「已载入正文的章节 id」，因为路由参数在切章瞬间就已改变，直接按路由 id 保存会把上一章的内容写进新章节。
- **版本快照**（复用 `draft_version`）：首次落笔自动留一版；之后自动保存只在字数差 ≥ 500 时留版；页面「保存快照」为手动留版，内容未变则跳过；每章最多保留 50 版，超出删最旧。恢复版本前会先把当前正文补成底稿（已有同内容快照则跳过），避免误点恢复丢稿。
- **页面边界**：写作台是作品内页面 `/projects/:projectId/write/:chapterId?`，路由名 `project-writing`；章节 id 写在路径上，缺失时只提示「从左侧选一章」并给出去大纲的入口，不自动回退到第一章。

## 4. UI 设计

### 4.1 视觉风格

贴合项目名 INK-HARNESS，采用**"纸墨"主题**：

- 米白纸色背景 `#F7F5F0`，墨色正文 `#1F1E1D`，青灰/朱砂点缀。
- 正文用衬线（思源宋体 / Noto Serif SC），界面用无衬线（Inter / 思源黑体）。
- 圆角克制、留白充足。
- 提供**专注模式**（隐藏所有 chrome，只留编辑区）与夜间模式。

### 4.2 全局框架

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏: 作品名 | 阶段进度(构思·大纲·初稿·编辑·出版) | 保存状态 | 导出/发布 │
├──────────┬───────────────────────────────────┬───────────────┤
│ 左侧导航  │            主内容区                 │  右侧 AI Copilot │
│ 章节树    │  (编辑器 / 大纲看板 / 设定库 / 报告) │  (对话+建议卡片)  │
│ 场景列表  │                                   │  (可折叠)       │
│ 设定入口  │                                   │               │
└──────────┴───────────────────────────────────┴───────────────┘
```

### 4.3 关键界面

1. **工作台 Dashboard**：作品卡片网格（封面、进度环、当前阶段、最近编辑时间）、"新建作品"、写作目标小组件、最近动态时间线。
2. **立项向导**：全屏分步表单，左侧步骤条，右侧对话式提问 + AI 实时生成结果预览卡。
3. **大纲看板**：按幕分列的看板，拖拽章节/场景卡；场景卡显示 POV/时间/地点/摘要/伏笔标记；右侧属性面板。
4. **设定库（两个独立页面）**：① 菜单入口 `/bible` 为**全局设定库**，汇总所有作品、只读、可按作品/类型/关键词筛选，并可跳到某部作品的设定库；② 作品卡片入口 `/projects/:projectId/bible` 为**作品设定库**，仅显示当前作品，左侧类型 Tab + 搜索、中间详情编辑、右侧关系图与一致性报告。两者不得共用同一页面或靠 query 切换作用域。
5. **写作台（核心页）**：顶部章节路径 + 字数 + 版本历史；中间 TipTap 编辑器，选中文本浮出 AI 工具条（续写/改写/扩写/润色）；右侧 Copilot 对话流式输出、建议卡片可一键采纳；底部显示后台 AI 任务状态。
6. **编辑/审稿**：左侧问题清单（按结构/一致性/语言筛选），中间原文 vs 建议的 Diff 视图（逐条接受/拒绝），右侧评分报告。
7. **出版中心**：Tab（排版预览 / 导出 / 封面与简介 / 发布清单），实时预览样式，生成物可下载。
8. **模型管理页**：Provider 卡片列表（本地/三方分组、状态灯、模型数、延迟）；添加向导（类型 → 地址/密钥 → 测试连接 → 拉取模型列表 → 勾选启用 → 能力标签）；任务路由表；用量与成本看板；本地模型下载/状态入口。
9. **设置**：Agent 角色管理（只定义 prompt 与工具权限，不绑定具体模型）、API Key、RAG、主题。

### 4.4 桌面化交互

- 原生菜单栏（文件/编辑/视图/帮助）、全局快捷键（⌘K 命令面板、⌘S 保存、专注模式切换）。
- 支持多窗口（主窗口 + 审稿报告独立窗口）、系统托盘（后台任务状态）。
- 文件拖拽导入参考资料、原生文件对话框选导出路径。
- 顶栏提供**本地 / 三方 / 混合**模式指示，一眼看清当前数据流向。
